# Why `/report` Sends 18 Antigravity Requests to the Daily Host

The `/report` command reaches Antigravity successfully, but all generation attempts fail with HTTP 429 `RESOURCE_EXHAUSTED`. The 18 requests are consistent with nested retry layers repeatedly targeting one effective proxy route, which forwards only to `daily-cloudcode-pa.googleapis.com` and does not fail over on a 429 response.

## Routing behavior

The observed traffic indicates that the client likely sees a single custom or proxy endpoint rather than multiple Google hosts:

- Custom endpoint configuration collapses the client’s candidate list to one host in `src/services/api/providers/gemini_code_assist.ts:92`.
- The proxy defaults to `daily-cloudcode-pa.googleapis.com` in `proxy/app.js:23`.
- The proxy switches to the production host only after an HTTP 404 response in `proxy/app.js:374`.
- An HTTP 429 response is returned directly instead of triggering host failover in `proxy/app.js:387`.

As a result, client-side cooldown and host reordering cannot redirect these requests. The client can only cool down or retry the proxy endpoint, while the proxy continues selecting the daily host.

## Why one command produces 18 requests

The request count matches the multiplication of four retry layers:

```text
1 effective client host
× 3 report sweeps
× 3 withRetry attempts
× 2 Gemini transport attempts
= 18 upstream requests
```

The relevant implementation points are:

- Three report sweeps: `src/commands/report/antigravityReport.ts:62-72`
- Three total `withRetry` attempts for a third-party 429, consisting of the initial attempt and two retries: `src/services/api/withRetry.ts:438-440`
- Two Gemini transport attempts: `src/lanes/gemini/api.ts:189-210`
- A fresh request ID generated for each transport attempt:
  - `src/lanes/gemini/api.ts:516`
  - `src/services/api/providers/gemini_code_assist.ts:1447`

This explanation depends on the runtime using a single custom or proxy endpoint. Runtime configuration is still needed to confirm that condition.

## What the 429 establishes

The available evidence confirms that:

- Antigravity rejects generation requests with HTTP 429 and status `RESOURCE_EXHAUSTED`.
- The error is classified as a retryable quota failure by:
  - `src/lanes/gemini/quota.ts:228`
  - `src/commands/report/presentation.ts:97-108`
- Every observed physical request reaches `daily-cloudcode-pa.googleapis.com`.
- No effective failover between Google hosts occurs.

The generic `RESOURCE_EXHAUSTED` response does not establish whether the underlying cause is:

- Account- or model-level quota exhaustion
- Rate limiting specific to the daily host
- Missing entitlement for the model used by `/report`

The `/usage` path only reads model-level `remainingFraction` in `src/services/api/antigravityUsageParser.ts:121-124`; it does not expose per-host generation limits. Missing model entitlement can also surface as HTTP 429, as handled in `src/services/api/providers/gemini_code_assist.ts:625-647`.

## Correction to the earlier host-sweep interpretation

A Gemini `prod → daily` sweep applies to direct client routing, not necessarily to the observed proxy configuration. When the client has only one proxy candidate, its cooldown logic affects that proxy rather than the Google hosts behind it, and the proxy does not switch hosts after a 429.

The default Gemini topology is `prod + daily`, as defined in `src/services/api/providers/gemini_code_assist.ts:128-142`; the Gemini sandbox is not a default candidate.

## Evidence still needed

The following information would distinguish the remaining explanations and confirm the routing model:

- Runtime values for:
  - `ANTIGRAVITY_BASE_URL`
  - `ANTIGRAVITY_HOST`
  - `TAU_ANTIGRAVITY_GEMINI_ENDPOINT`
- The exact model ID selected by `/report`
- The entitled-model list returned by Antigravity quota or onboarding APIs
- The complete 429 response headers, especially quota metadata and `Retry-After`
